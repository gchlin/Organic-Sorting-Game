Game V2 重構：為什麼要做，現在做到哪裡？

簡單說：這次重構不是為了把遊戲變華麗，而是為了讓遊戲規則更穩、更好改、更不容易改一個地方壞三個地方。 目前 V2 已經接上主遊戲，接下來最重要的是測試、清理、修正細節。

目前狀態：V2 已是主線

index.html 現在載入 game-v2.js，舊版 game.js 已搬到 legacy/。

接下來重點：驗證玩法

Practice、Duel、Dynamic、AI、存檔與輸入鎖都要用 checklist 一項項跑過。

最大風險：文件比實作還亂

有些舊文件提到 Speed 或早期規則，現在要以 README 與實際遊戲行為交叉確認。

一句話版

以前遊戲像「所有規則、畫面、計時器、按鍵都塞在同一鍋」。V2 是把它拆成比較清楚的區塊： 規則歸規則、狀態歸狀態、題目歸題目、動畫計時歸動畫計時。

這樣以後你想加新模式、調 AI、改 Duel 規則、修答題 bug，不會每次都像在拆炸彈。

為什麼需要重構？

1. 遊戲規則需要穩

Practice、Duel、Dynamic、AI 都有不同節奏。如果規則散在很多函式裡，很容易出現「答錯、逾時、搶答」互相打架。

2. 避免 timer 決定遊戲

動畫和倒數應該只是效果。真正決定誰能答、何時換人、何時揭曉答案的，應該是遊戲狀態。

3. 讓 AI 和真人走同一條路

AI 不應該有秘密捷徑。它應該像玩家一樣送出「搶答」和「作答」動作，這樣比較公平，也比較好 debug。

4. 以後比較好加東西

如果新功能只要改規則表或某個小模組，就不需要一直碰巨大的主檔，心情會好很多。

現在已經做了什麼？

項目 目前看起來的進度 白話意思
game-v2.js 已接上 主遊戲現在跑 V2，不是舊版 legacy/game.js。
mode-rules.js 已建立 Practice、Speed、Duel 的規則數值被集中起來。不過 Speed 是否保留，仍要跟目前 README 規格對齊。
game-state.js 已建立 玩家分數、目前題目、搶答狀態、Dynamic 狀態、輸入鎖都開始集中管理。
question-engine.js 已建立 抽題、選項、答案檢查已拆出來，這是讓 Practice 和 Duel 共用題目邏輯的基礎。
effect-manager.js 已建立 timer、動畫殘留、暫態 class 清理集中處理，降低「上一題效果殘留到下一題」的機率。
input-controller.js 已建立 鍵盤、點擊、搶答會先變成 action，再交給遊戲處理。這讓輸入比較可控。
ai-controller.js 已建立 PvE AI 已有獨立控制器，目標是讓 AI 像真人一樣送出 action。
docs/refactor-test-checklist.md 待人工跑完 這份是測試清單。它不是程式完成證明，而是用來確認 V2 真的穩。

所以它已經完成了嗎？

比較準確的說法是：主要骨架已完成，而且 V2 已經接到遊戲入口；但還不能當作完全驗收完成。 因為重構最容易出問題的不是「檔案有沒有拆出來」，而是「所有玩法邊界情境是否都正常」。

我會把它分成三種狀態

  • 已完成：V2 主檔接上、核心模組存在、舊版移到 legacy/。
  • 需要驗證：Practice 通關、Duel 搶答、Dynamic 暫停/恢復、AI 行為、存檔解鎖、輸入鎖。
  • 需要整理：README、舊 doc、實際程式之間有些規則可能不同步，尤其是 Speed 是否保留。

現在最重要的決策

你現在最需要決定的不是「要不要整理全部」，而是： 接下來 1 到 2 週，專案的主線到底是穩定遊戲，還是繼續改 UI？

我的建議是先選 穩定遊戲主線。原因很簡單：如果遊戲狀態會殘留，UI 再漂亮也會讓人覺得不穩。 但這不代表 UI 不重要，而是 UI 先進入「只修最痛點」模式。

推薦主線：先穩定遊戲

先修 Duel 下一題殘留、輸入鎖、timer cleanup、答題流程。這些是玩家會立刻感覺到的 bug。

UI 支線：只修阻礙體驗的地方

手機/桌機比例先不要大 redesign，只先處理文字爆版、圖片太大太小、按鈕難按。

目前最大的模糊點

1. 哪一個 branch 才是「真主線」？
你現在 game logic branch 和 UI branch 交替做，最容易造成兩邊都各自前進，但最後很難合併。 建議指定一條 integration branch 當真主線，其他 branch 都只做短任務。
2. README / docs / 程式碼誰說了算？
文件有歷史痕跡，程式碼也有過渡狀態。短期建議：以目前遊戲入口 index.html + 實際可玩行為為準， README 只當規格草稿，舊 docs 當歷史資料。
3. V2 到底算完成還是未完成？
架構接上了，但驗收未完成。也就是「已進入 V2 時代」，但還不是「V2 穩定版」。
4. CSS 要不要現在整個拆掉？
不建議一次全部拆。先建立新 CSS 分區，之後每修一個畫面，就把相關樣式搬到對應檔案。 這樣風險小，也比較不會卡住。
5. 要不要同時修 logic 和 UI？
可以，但要分層：logic bug 優先進主線；UI 只修最影響遊玩的痛點。不要在同一個 commit 同時大改規則和大改 layout。

互動路線選擇

點一個你現在的狀態，下面會給你最適合的下一步。

建議：只做「確認主線 + 一個小修」

今天不要讀完整專案。只確認目前主線是哪個 branch，然後挑一個明確 bug，例如 Duel 下一題殘留。

目標不是變乾淨，是先讓你重新有掌控感。

檔案怎麼分工？

mode-rules
放「規則數字」和「模式設定」。例如一局幾題、Duel 幾分贏、答題時間幾秒。
game-state
放「現在遊戲到底在什麼狀態」。例如誰搶到、誰被鎖、目前題目是什麼。
question-engine
處理題目和答案。它不管畫面漂亮不漂亮，只回答「這題是什麼、選項是什麼、選對了嗎」。
effect-manager
管理倒數、動畫、清理殘留。它像舞台工作人員，確保上一幕收乾淨才進下一幕。
input-controller
把鍵盤、滑鼠、觸控變成遊戲 action。先統一語言，遊戲邏輯才好處理。
ai-controller
AI 專用。它不偷改遊戲，只模擬玩家送出搶答和作答。

下一步最重要的 5 件事

  • 打開遊戲，跑一輪 Practice：確認題目、答案、通關、解鎖、錯題都正常。
  • 跑 Duel Standard：確認搶答、5 秒答題、答錯換人、先到 5 分。
  • 跑 Duel Dynamic：確認搶答前動畫、搶答後暫停、答錯/逾時後恢復或換人。
  • 測 PvE AI：確認 AI 不會卡住、不會在不能答題時偷答。
  • 整理文件：把「已過期的 refactor 計畫」和「目前真實狀態」分清楚。

你的實際開發順序

這個順序比「先讀完整專案」健康很多。它先照顧你的工作感受，再處理規則正確性。

1. 顯示 UI 友善
先讓畫面在手機和電腦都看得懂、按得到、文字不爆版。這一步不是追求完美設計，而是讓測試變得不痛苦。
2. 修明顯 bug
修玩家一眼就會感覺怪的問題，例如 Duel 下一題瞬間殘留上一題、按鍵卡住、動畫沒清乾淨。
3. 符合教學需求
確認題庫、選項池、誘答選項、答案說明真的能用在教學上，而不只是程式可以跑。
4. 修小 bug
最後再處理比較細的邊角問題，例如特殊尺寸、重複點擊、少數題目資料怪怪的。

目前該人工測試的清單

這份不是工程驗收表，而是「你可以照著玩一遍」的測試路線。先測最影響體驗的，再測規則細節。

第一輪：UI 友善度

  • 手機直式：主選單、選關、遊戲畫面、設定視窗是否看得懂。
  • 手機橫式：分子圖、題目文字、四個選項是否比例合理。
  • 桌機：畫面是否太空、太擠，或重要資訊分散太遠。
  • 選項按鈕：文字長一點時是否爆版，手指是否容易點。
  • 分子圖片：是否太小看不清，或太大擠掉題目和選項。
  • Duel 畫面：兩位玩家的分數、狀態、搶答提示是否清楚。
  • Modal：教學、Codex、設定、確認視窗是否在手機上可讀可關。

第二輪：明顯 bug

  • Duel 下一題開始時，不應瞬間殘留上一題圖片、答案、高亮或動畫。
  • 答題後 feedback 期間，連點或狂按鍵不應造成重複作答。
  • 換題後，上一題的正確/錯誤 class 應該全部清掉。
  • Dynamic 暫停、恢復、揭曉答案後，不應留下多餘倒數或動畫元素。
  • 離開遊戲再進入同模式，不應保留上一局分數、timer、buzz 狀態。
  • 設定、返回、重新開始，不應讓遊戲卡在不能按的狀態。

第三輪：教學上真的能用

  • 每一題的正確答案是否符合有機化學分類。
  • 四個選項是否有合理誘答，而不是太簡單或太離題。
  • 同一關的題目難度是否從基本到進階有教學節奏。
  • 錯誤答案是否能幫學生理解差異，例如 alcohol / phenol / ether 不混亂。
  • 題庫是否有足夠變化，不會一直抽到類似題。
  • Practice 通關條件是否符合你的教學目的，而不是只追求遊戲性。
  • Codex / 解鎖內容是否能支援複習，不只是收集品。

第四輪：小 bug 與整理

  • 快速切換模式、返回主選單、重新開始，是否有殘留狀態。
  • 不同瀏覽器或不同螢幕比例是否有文字重疊。
  • 音效、動畫、震動感是否會過度干擾答題。
  • 存檔匯入/匯出、重置進度是否還正常。
  • console 是否出現明顯錯誤。

給 vibe coder 的判斷方式

你不用先讀完所有工程文件。可以照這個順序看：

  • 想知道「現在遊戲用哪個版本」：看 index.html 最下面 script，現在是 game-v2.js。
  • 想知道「規則在哪」：看 mode-rules.js。
  • 想知道「按鍵或點擊怎麼進遊戲」：看 input-controller.js。
  • 想知道「為什麼動畫或 timer 怪怪的」：先看 effect-manager.js。
  • 想確認「真的穩不穩」：照 docs/refactor-test-checklist.md 玩一遍。

我建議怎麼處理舊文件

docs/refactor-architecture.md 比較像「當初要怎麼做」； 這份 HTML 則是「現在你要怎麼理解它」。

如果你之後要繼續開發，我建議把舊文件標成三類：

目前規格 歷史計畫 測試清單

這樣未來不會看到一份舊 plan 就以為還沒做，也不會看到檔案存在就以為已經完全驗收。
